## 원인 확인 결과와 한계

기존 `cloud_store.database_request()`는 서버 환경변수 `DATABASE_URL`이 없거나 빈 값이면 정확히 **공유 데이터베이스가 연결되지 않았습니다.**를 반환했습니다. 직원 비밀번호, 세션 쿠키 검증이 실행되기 이전의 서버 설정 검사입니다. 따라서 이 문구를 잘못된 직원 비밀번호나 집 PC의 로컬 DB 문제로 판단하면 안 됩니다.

다만 이번 점검 시작 시 공식 주소에서는 이미 `storage_configured=true`, 로그인 페이지 HTTP 200, 인증 상태 API HTTP 200이 확인됐습니다. 사용자가 집에서 겪은 그 시점의 장애는 현재 재현되지 않았습니다. 기존 저장소 예외 처리에는 해당 오류의 조회번호와 구조화 로그가 없었고 Vercel 무료 플랜의 과거 로그 보존·조회 범위 제한도 있어, **당시 어떤 배포에서 설정이 빠졌는지 또는 어떤 배포 변경이 원인이었는지까지 확정하지는 못했습니다.**

최근 조회 가능한 런타임 표본 100건에는 storage_request_failed 이벤트가 없었습니다. 이 표본만으로 과거에 장애가 없었다고 결론내리지는 않습니다. 과거 전체 로그 조회 시 나타난 HTTP 402는 Vercel의 로그 조회 기능 요금제 제한이며, Supabase DB가 사용 한도로 막혔다는 증거가 아닙니다. 유료 플랜으로 변경하지 않았습니다.

## 실제 DB 구조

- 공용 원본 저장소는 **Supabase PostgreSQL**입니다.
- 실제 사용 중인 연결은 **Transaction pooler / 6543 포트 / SSL require**이며 `prepare_threshold=None`으로 사용합니다.
- PostgreSQL `baton_demo_state`의 bytea 컬럼에 기존 SQLite 스냅샷을 저장합니다. 각 요청은 Vercel의 임시 폴더에 복제하여 처리하고, 변경이 있으면 PostgreSQL에 원자적으로 저장합니다. 인증·캐시 사용 전에도 서버 DB 버전을 확인합니다.
- 회사 PC의 로컬 SQLite 파일을 Vercel이 원격으로 읽는 방식은 아닙니다. 회사와 집의 브라우저는 같은 Vercel 백엔드와 공용 Supabase를 사용합니다.
- 반면 `실행하기.cmd`로 시작하는 로컬 앱의 데이터와 공개 사이트 데이터는 별도일 수 있습니다. 로컬 DB를 이번 작업에서 복사·삭제·덮어쓰지 않았습니다.
- 현재 저장소는 네이티브 PostgreSQL 업무 테이블로 완전히 변환된 구조는 아닙니다. 기존 SQLite SQL을 유지하는 스냅샷 어댑터 구조이며, 단일 상태 행 잠금과 20MB 스냅샷 제한이 있습니다.
- 기존 Neon DB 및 과거 보존 데이터는 변경하지 않았습니다. 오래된 POSTGRES_URL 등은 현재 연결 선택에 자동 사용하지 않습니다. **DATABASE_URL 한 항목을 명시적으로 사용**합니다.

참고: [Supabase 공식 서버리스 연결 안내](https://supabase.com/docs/guides/database/connecting-to-postgres/serverless-drivers)

## 수정 내용

1. `cloud_database_config.py`: 누락·잘못된 PostgreSQL URL·운영 환경의 localhost 주소 검사. 다른 DB나 로컬 DB로 자동 대체하지 않습니다.
2. `tools/validate_cloud_environment.py`, `vercel.json`: DATABASE_URL이 없거나 형식이 틀린 새 배포를 빌드 단계에서 중단합니다. 기존 정상 배포와 DB는 유지합니다. 실제 접속 가능 여부는 별도의 읽기 전용 상태 API에서 확인합니다.
3. `cloud_store.py`: 운영 환경에서 빈 상태 행이나 빈 스냅샷을 새 데이터로 초기화하지 않고 명확하게 중단합니다. 가상 계정 초기화는 기존의 격리 자동 테스트에서만 사용합니다.
4. `api/index.py`: 읽기 전용 `/api/system/storage-status` 추가. 상태·제공업체·풀러 여부·실행 버전만 공개하며 계정 수·호스트·프로젝트 식별자·접속 문자열·비밀번호는 반환하지 않습니다.
5. `storage_diagnostics.py`: 설정 누락, DB 인증 오류, 미초기화 DB, 사용 한도, 일반 연결 실패를 구분합니다. 코드·오류 조회번호·안전한 예외 종류·SQLSTATE·배포 정보만 로그에 기록합니다. 요청/응답 원문·계정 비밀번호·API 키는 기록하지 않습니다.
6. `web/login.js`, `web/login.html`: 연결 오류 조회번호 표시 및 사용자 선택형 연결 재확인. 입력은 유지하고 자동 반복 요청은 하지 않습니다.
7. `web/workflow.js`, `web/ui.js`, `web/index.html`: DB 장애를 로그인 만료로 잘못 표시하지 않도록 구분하고, 공개 서비스 오류에서 로컬 실행 창을 요구하는 잘못된 안내를 정리했습니다. 인증 우회나 캐시 인증은 추가하지 않았습니다.
8. 설정·민감정보 비노출·쿠키 보존·누락 배포 중단·빈 DB 미초기화 테스트와 브라우저 오류 복구 테스트를 추가했습니다.

## Vercel 환경변수

필수 항목은 **DATABASE_URL**입니다. Vercel 프로젝트 `botontouch-test`의 **Settings → Environment Variables → Production**에 Supabase Connect 화면의 승인된 Transaction pooler 연결 문자열을 Secret으로 저장합니다. 이번 확인에서는 이미 설정되어 있어 원문을 출력하거나 다른 DB 주소로 바꾸지 않았습니다.

회사 PC의 환경파일만 변경해서는 Vercel 설정이 바뀌지 않습니다. Vercel 환경변수를 바꾼 경우에는 새 Production 배포가 필요합니다. Preview를 별도로 운영하려면 승인된 별도 테스트 DB 설정을 준비해야 하며, 운영 직원 DB를 무조건 복사해 연결하지 않습니다.

기존 Gemini 키·모델·외부 전송 승인 설정과 세션 보안 설정은 유지했습니다. 새로 입력해야 할 추가 비밀 환경변수는 없습니다.

## 집에서 다시 확인하는 방법

1. 공식 로그인 주소에서 새로고침한 뒤 로그인합니다. 회사와 집의 로그인 쿠키가 서로 다른 것은 정상입니다. 자료 저장소는 같습니다.
2. 문제가 남으면 DB 상태 주소를 엽니다. `status: ready`이면 해당 배포 서버에서 공용 DB 연결을 확인한 상태입니다.
3. 오류가 다시 나오면 화면의 오류 조회번호와 발생 시각만 전달합니다. 비밀번호·쿠키·API 키는 보낼 필요가 없습니다.
4. 현재 운영 DB 주소를 새로 만들거나 데이터베이스를 초기화할 필요는 없습니다.

## 향후 네이티브 PostgreSQL 전환 방안

이번에는 안전을 위해 저장 구조를 변경하지 않았습니다. 장기적으로는 읽기 전용 백업으로 직원·문서·질문·요청·채팅 테이블을 PostgreSQL로 분리 이관하고, 원래 ID와 직원 매핑 및 해시를 그대로 보존해야 합니다. 건수·내용 해시·권한·문서/채팅 연결을 복제 환경에서 대조한 후 읽기 경로부터 단계적으로 전환하고, 원본 스냅샷은 롤백용으로 유지합니다. 첨부파일은 승인된 영속 저장소로 분리할 수 있습니다. 이를 통해 큰 스냅샷 전송과 단일 상태 행 잠금을 줄일 수 있습니다.

## 증거 파일

로컬 `artifacts/external-db-recovery/`에 검증 결과와 가상자료 화면을 저장했습니다. 민감한 과거 런타임 원본이나 DB 백업은 공개 저장소에 올리지 않고 `data/private/external-db-diagnostics/`에서만 보관합니다.
