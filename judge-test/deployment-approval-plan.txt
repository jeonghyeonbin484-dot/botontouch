바통터치 심사용 계정 — 운영 변경 승인안

확인 결과
- 현재 운영 설정은 일반 개발용 is_test 계정의 로그인을 차단합니다.
- 실제 직원과 심사용 계정 사이의 발송을 확실히 차단하는 별도 정책은 없습니다.
- 계정만 추가하거나 개발용 차단을 전체 해제하는 방식으로 진행하지 않습니다.

승인 요청 범위
1. 현재 배포 기준 코드에 심사용 계정 2개만 허용하는 서버 정책을 추가합니다.
2. 로그인은 기존 비밀번호 해시·실패 횟수 제한·세션 정책을 사용합니다. 일반 직원의 인증은 바꾸지 않습니다.
3. 테스트 표식(is_test), 가상 부서·직원 식별값과 정확한 두 계정의 조합을 검사합니다. 관리자 권한을 부여하지 않습니다.
4. 부서·직원 조회는 두 가상 직원으로 제한하고, 요청 발송 시 양쪽 모두 같은 심사용 그룹인지 백엔드에서 검사합니다. 실제 직원 → 테스트 계정, 테스트 계정 → 실제 직원 발송을 모두 차단합니다.
5. DB 스키마는 바꾸지 않습니다. 비공개 백업 후 새 계정 2개·가상 직원 2명·가상 부서 1개와 그 계정의 심사용 업무 기록만 추가합니다. 이름이 겹치면 기존 계정을 덮어쓰지 않고 중단합니다.
6. 계정마다 서로 다른 무작위 비밀번호를 해시로 저장하고 실제 로그인 확인 후 별도 안내 파일에만 기록합니다. 기존 실제 직원 계정·비밀번호·문서·대화는 변경하거나 삭제하지 않습니다.
7. 검증된 최신 배포본에 필요한 제한만 반영합니다. 미완료 리팩터링 변경은 함께 배포하지 않습니다.
8. 복제 DB·가상자료로 권한 차단 검사 후 GitHub와 기존 Vercel 사이트에 최소 변경을 배포합니다. 비밀번호와 실제 직원정보는 포함하지 않습니다.
9. 승인 후 배포 사이트에서 실제 Gemini 기능 요청을 최대 4회 수행합니다. 기존의 일시적 503 재시도는 별도로 기록하고, 실패를 모의 성공으로 표시하지 않습니다.
10. 실제 인계·인수·질문·답변·완료·다운로드까지 검증하고, 생성된 계정 2개는 심사용으로 유지합니다. 검증 과정에서 새로 생긴 심사용 기록은 별도로 표시합니다.

아직 실행하지 않은 작업
- 계정 생성, 운영 DB 추가, 설정 활성화, GitHub 반영, 배포, 실제 Gemini 호출.

승인 후 복귀 방법
- 심사용 허용 설정을 비활성화하여 두 계정 사용을 막을 수 있도록 합니다.
- 문제가 있으면 직전 배포로 되돌립니다. 기존 운영 데이터는 삭제하거나 백업으로 덮어쓰지 않습니다.
